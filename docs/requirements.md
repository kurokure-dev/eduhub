\# EduHub 요구사항



\## 개요

임직원이 사내 교육과정을 조회·신청하고, 정원이 차면 대기자로 등록되는 시스템.

\- 사용자: 임직원(수강생), 교육 담당자(관리자)



\## 기술 스택

\- 백엔드: Java 21, Spring Boot 3, Spring Data JPA, Flyway, springdoc-openapi, SQL Server

\- 프론트엔드: React 18 + TypeScript, Module Federation(shell, course-mfe, enrollment-mfe), MUI, Axios

\- 빌드: Gradle(Kotlin DSL), npm workspaces



\## 기능 요구사항 (무엇을 하는가)

| ID | 요구사항 | 사용자 | 우선순위 | 주차 |
|---|---|---|---|---|
| FR-01 | 교육과정 목록을 조회하고 제목·분류로 검색한다 (페이지 단위) | 임직원 | 필수 | 2 |
| FR-02 | 과정 상세와 회차(일정, 장소, 정원, 남은 자리)를 조회한다 | 임직원 | 필수 | 2 |
| FR-03 | 관리자는 과정과 회차를 등록·수정·종료한다 | 관리자 | 필수 | 2 |
| FR-04 | 회차에 수강 신청한다. 같은 회차에 중복 신청할 수 없다 | 임직원 | 필수 | 3 |
| FR-05 | 정원이 차면 대기자로 등록되고 대기 순번을 알려 준다 | 임직원 | 필수 | 3 |
| FR-06 | 신청을 취소하면 대기 1순위가 자동으로 신청 확정된다 | 임직원 | 필수 | 3 |
| FR-07 | 내 신청 내역(확정, 대기, 취소, 수료)을 조회한다 | 임직원 | 필수 | 4 |
| FR-08 | 관리자는 회차별 신청자·대기자 명단을 보고 수료 처리한다 | 관리자 | 보통 | 4 |
| FR-09 | 신청 확정·대기 승급·대기 강등 시 알림을 남긴다 (처음에는 로그·DB 기록) | 임직원 | 선택 | 5 |



\## 비기능 요구사항 (얼마나 잘, 어떤 제약 아래서)

| ID | 분류 | 요구사항 | 확인 방법 |
|---|---|---|---|
| NFR-01 | **정합성** | 동시에 100명이 마지막 1자리에 신청해도 정원을 넘지 않는다 | 동시성 테스트 |
| NFR-02 | **성능** | 과정 목록 API는 데이터 1만 건에서 응답 300ms 이내, N+1 쿼리 없음 | 쿼리 로그, 성능 테스트 |
| NFR-03 | **보안** | 로그인한 사용자만 신청 가능, 본인 신청만 취소 가능, 비밀 정보는 저장소에 두지 않음 | 테스트, 비밀 검사 |
| NFR-04 | **API 계약** | 모든 API는 OpenAPI 문서가 있고, 프론트 클라이언트는 스펙에서 생성한다 | Swagger UI, 생성 스크립트 |
| NFR-05 | **품질** | 서비스 계층 테스트 커버리지 70% 이상, CI에서 빌드·테스트·포맷 검사 | CI 결과 |
| NFR-06 | **운영성** | 개발·테스트·운영 설정 분리, 사람이 직접 실행할 수 있는 빌드·배포·롤백 절차 문서 | 런북, 핫픽스 훈련 |
| NFR-07 | **유지보수성** | 도메인별 패키지(course, enrollment), 계층 규칙 준수, 화면은 MFE로 분리 | 리뷰, 아키텍처 테스트 |
| NFR-08 | **이해도** | 팀원 누구나 AI 없이 구조와 핵심 파일의 역할을 설명할 수 있다 | 발표 시 확인 |



\## 결정 사항

| ID | 주제 | 결정 | 관련 |
|---|---|---|---|
| D-01 | 취소 | 확정자와 대기자 모두 취소할 수 있다. 대기자가 취소하면 뒷순번이 하나씩 앞당겨진다 | FR-05, FR-06 |
| D-02 | 취소 기한 | 취소는 회차 마감(종료) 전까지만 할 수 있다. 회차의 시작·끝 시점은 따로 관리하지 않는다 | FR-06, D-11 |
| D-03 | 수료 | 확정자만 수료 대상이며, 수료 처리는 관리자만 할 수 있다 | FR-08 |
| D-04 | 회차 종료 | 회차를 종료하면 남은 대기 신청은 자동 취소된다. 종료된 회차에는 신청할 수 없다 | FR-03 |
| D-05 | 정원 증가 | 정원이 늘면 늘어난 수만큼 대기자를 순번대로 자동 승급한다 | FR-03, FR-06 |
| D-06 | 정원 감소 | 정원이 줄면 넘치는 인원만큼 하위 순번 확정자를 대기로 바꾼다 | FR-03, FR-05 |
| D-07 | 재신청 | 취소한 회차에 다시 신청할 수 있으며, 대기가 되면 순번은 맨 뒤다 | FR-04 |
| D-08 | 다른 회차 | 같은 과정의 다른 회차에 동시에 신청할 수 있다 | FR-04 |
| D-09 | 대기 순번 표시 | 신청 내역을 조회하면 현재(바뀐) 대기 순번을 보여 준다 | FR-05, FR-07 |
| D-10 | 수료 시점 | 수료 처리는 회차 마감 뒤라면 언제든 할 수 있다. 수료하지 못한 확정자는 확정 상태로 남는다 (별도의 미수료 상태는 두지 않는다) | FR-07, FR-08 |
| D-11 | 종료의 의미 | 회차 "종료"는 모집 마감이다. 종료 전까지 대기자는 그대로 남는다 | FR-03, D-04 |
| D-12 | 강등 기준 | 정원이 줄면 신청 시각이 늦은 확정자부터 대기로 바꾸고, 내려간 사람은 대기 맨 앞 순번이 된다. 여러 명이 함께 내려가면 그중 신청 시각이 이른 사람이 앞 순번이다 | D-06 |
| D-13 | 강등 알림·정원 변경 시점 | 확정에서 대기로 바뀔 때도 알림을 남긴다. 정원은 회차 마감 전까지만 바꿀 수 있다 | FR-03, FR-09 |
| D-14 | DB 종류 | 프로젝트 DB는 PostgreSQL이 아니라 SQL Server다 (개발 DB: SGY_EHUB). 한글을 저장하므로 문자열 컬럼은 NVARCHAR로 만든다 | NFR-01, NFR-06 |
| D-15 | 테스트 DB | DB 테스트는 Testcontainers 없이 개발 DB(SGY_EHUB)에 직접 연결한다. 접속 정보는 dev와 같은 `.env`를 쓰고, 테스트 데이터는 롤백으로 남기지 않는다 | NFR-01, NFR-05 |
